## Security review

### Threat / abuse cases (in scope)

| Case | Assessment |
| --- | --- |
| Cross-owner read via aggregate API | **Denied** — `withActor(ownerUserId)` + RLS `tickets_owner_actor_select` + query `WHERE owner_user_id = $owner`; test proves actor B cannot list A’s rows even with A’s UUID in SQL |
| Cross-tenant **mutation** opened by new SELECT policy | **Denied** — policy is `FOR SELECT` only; `tickets_isolation` retains `USING`/`WITH CHECK` on `app.tenant_id` for writes; UPDATE/DELETE still require `withTenant` |
| `app.actor_id` from client query/header | **Denied** — GUC set only in `withActor` from server-mapped `user.userId` after bearer verify |
| Unset / empty GUC | **Denied** — `NULLIF(current_setting('app.actor_id', true), '')` → no rows match |
| Pool connection reuse leaking GUC | **Mitigated** — `set_config(..., true)` transaction-local; existing `rls.test.cjs` pool-reuse checks still pass |
| `BYPASSRLS` on runtime role | **Denied** — aggregate test asserts `rolbypassrls = false`; migration grants policy only to `ticket_runtime` |
| Parameterized SQL / injection | **OK** — Prisma `$queryRaw` tagged template for `ownerUserId` |

### RLS design

Migration adds:

```sql
CREATE POLICY tickets_owner_actor_select ON tickets
  FOR SELECT TO ticket_runtime
  USING (owner_user_id = NULLIF(current_setting('app.actor_id', true), '')::uuid);
```

Existing `tickets_isolation` remains. PostgreSQL OR-combines permissive SELECT policies → owner sees owned rows across tenants when `app.actor_id` is set; tenant-scoped callers still work via `tickets_isolation` when `app.tenant_id` is set.

**Verdict (security):** **PASS** — intentional, bounded cross-tenant read for verified owner; mutations unchanged; tests exercise real Postgres (Docker) in `me-tickets-aggregate.test.cjs`.
