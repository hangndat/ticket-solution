# Portal fixture contract (manifest schemaVersion 1)

All cases use `cases[caseId]` from the shared manifest. Every case needs a separate tenant/event and independent mutable records. `tenantId` and `eventId` must be UUIDs; `tenantSlug` and `eventSlug` identify the corresponding event. Accounts are real Keycloak users; `owner`, `manager`, `cs`, and `operator` need verified email. The browser origin is `origins.portal` over HTTPS with a distinct `auth` hostname and valid OIDC issuer/redirect. Do not seed a production or shared development stack.

Case-specific `data` keys used by specs and additional provisioning requirements:

`PORT-11` is a staff membership invitation and must be checked through the real worker and Mailpit. It is distinct from `WEB-13` guest invitation/claim. Provider status assertions must use only `PENDING`, `ACCEPTED`, `FAILED`, `DEAD`, `UNKNOWN`; `ACCEPTED` means transport accepted, not inbox delivery/read. Retry-After assertions apply only on endpoints that actually send that header.

The current shared harness exposes the manifest contract and test imports but no provisioned manifest/runtime. Until the coordinator supplies isolated HTTPS origins, case records, and actual worker/Mailpit, runtime results are **BLOCKED**. Source-based or discovery checks do not count as browser/API PASS.
